# Super 플래너 프로젝트 구조 학습 문서

이 문서는 **웹 개발이 처음**이거나 **이 프로젝트가 어떻게 굴러가는지 큰 그림이 필요한 사람**을 위해 작성되었습니다. 모든 폴더와 핵심 파일이 어떤 일을 하는지, 사용자가 버튼을 누르면 어떤 흐름으로 데이터가 움직이는지 설명합니다.

---

## 0. 시작하기 전에 — 웹 앱이란

웹 앱은 크게 **두 부분**으로 나뉩니다.

```
[브라우저 (사용자 PC/휴대폰)]   ←→   [서버 (이 프로젝트가 도는 PC)]
       프론트엔드                       백엔드 + 데이터베이스
       Next.js 가 만든 HTML/JS                 Next.js API + SQLite
```

비유:
- **브라우저** = 음식점 손님이 보는 메뉴판/테이블
- **서버** = 주방
- **API** = 주문서 (손님이 "비빔밥 하나" 라고 적어 보내면 주방에서 만들어 보냄)
- **데이터베이스(DB)** = 식재료 창고 (재료 꺼내고 보관)

이 프로젝트는 **하나의 PC** 가 주방+창고+서빙까지 다 합니다 (self-hosted). 손님은 인터넷으로 멀리서 접속.

## 1. 사용된 기술 스택 (도구)

| 도구 | 역할 | 왜 이걸 쓰나 |
|---|---|---|
| **Next.js 16** | 프론트엔드 + 백엔드 통합 프레임워크 | 한 프로젝트로 화면+API 둘 다. App Router 라는 새 방식 사용 |
| **React 19** | UI 부품(컴포넌트) 만드는 라이브러리 | 화면을 작은 조각으로 나눠서 조립 |
| **TypeScript 5** | JavaScript + 타입 검사 | "잘못된 데이터" 를 코드 작성 단계에서 잡아냄 |
| **Tailwind CSS v4** | 스타일링 (디자인) | `className="text-blue-500"` 처럼 클래스로 빠르게 디자인 |
| **SQLite** | 파일 한 개짜리 DB | 별도 서버 불필요, `data/binder.sqlite` 한 파일에 모든 데이터 |
| **better-sqlite3** | Node.js 에서 SQLite 다루는 라이브러리 | 빠르고 동기적 |
| **Drizzle ORM** | SQL 을 TypeScript 로 작성 | `db.select().from(todos)` 처럼 안전한 SQL |
| **iron-session** | 쿠키 기반 로그인 세션 | 로그인 정보를 암호화된 쿠키에 |
| **argon2** | 비밀번호 해시 | 비밀번호를 절대 평문으로 저장 안 함 |
| **lucide-react** | 아이콘 모음 (`<Plus />`, `<Calendar />` 등) | 가벼운 SVG 아이콘 |
| **Vitest** | 단위 테스트 도구 | `npm test` 로 작은 함수 검증 |
| **Playwright** | E2E (End-to-End) 테스트 | 실제 브라우저 자동화로 시나리오 검증 |
| **Docker** | 컨테이너 (앱을 격리된 환경에 담음) | 어디서든 똑같이 실행 |
| **Caddy** | 리버스 프록시 + HTTPS | 인터넷 → Caddy → 앱 |

## 3. 데이터 흐름 — "todo 하나 추가하면 어떤 일이 일어나는가"

가장 직관적인 예. 사용자가 주간 페이지에서 "할일 하나" 입력 + 엔터:

```
1. [브라우저] 사용자가 input 에 "운동" 입력 + Enter
   ↓
2. [브라우저: components/week/DayTodoColumn.tsx]
   onSubmit 핸들러 발동, createTodo({ title:'운동', scope:'day', ... }) 호출
   ↓
3. [브라우저: lib/repo/todos.ts]
   createTodo 가 fetch('/api/todos', POST, body) 호출
   ↓ HTTPS 요청
4. [서버: proxy.ts]
   요청을 가로채서 쿠키 검증 → 로그인 OK 확인 → 통과
   ↓
5. [서버: app/api/todos/route.ts]
   POST 핸들러:
     - requireSession() 으로 session.userId 추출
     - body 의 데이터 + userId 로 createTodo(server) 호출
   ↓
6. [서버: lib/server/repos/todos.ts]
   createTodo 가 Drizzle 로 SQL INSERT 실행
   ↓
7. [DB: data/binder.sqlite]
   todos 테이블에 새 행 추가 (user_id = 현재 사용자)
   ↓
8. [서버] DB 결과를 JSON 으로 응답
   ↓ HTTPS 응답
9. [브라우저: lib/repo/todos.ts]
   응답을 받아 새 Todo 객체 반환
   ↓
10. [브라우저: components/week/DayTodoColumn.tsx]
    setState 로 화면에 새 todo 추가
```

이게 **모든 기능의 기본 패턴**입니다. 만다라트 목표 추가, 시간블록 생성, 회고 저장 등 모두 같은 9~10단계.

## 4. 핵심 폴더 자세히

### 4.1 `app/` — 화면과 API

Next.js 16의 **App Router** 방식. 폴더 이름이 곧 URL 이 됩니다.

```
app/
├── layout.tsx                  ← 모든 페이지 공통 레이아웃 (HTML <html>, <body>)
├── page.tsx                    ← / (루트) 페이지
├── globals.css                 ← 전역 CSS
├── manifest.ts                 ← PWA(웹 앱 설치) 메타데이터
├── login/
│   └── page.tsx               ← /login 화면
├── (app)/                      ← 괄호: URL에 안 들어감, 그룹핑
│   ├── layout.tsx              ← 로그인 후 페이지들의 공통 레이아웃 (네비 포함)
│   ├── mandalart/
│   │   └── page.tsx           ← /mandalart
│   ├── annual/
│   │   └── [year]/
│   │       └── page.tsx       ← /annual/2026 (대괄호: 동적 URL 파라미터)
│   ├── monthly/[yyyymm]/page.tsx
│   ├── week/[isoweek]/page.tsx
│   ├── retrospective/...
│   ├── reading/page.tsx
│   └── settings/page.tsx
└── api/
    ├── auth/
    │   ├── login/route.ts     ← POST /api/auth/login
    │   ├── logout/route.ts    ← POST /api/auth/logout
    │   └── me/route.ts        ← GET /api/auth/me (현재 사용자 정보)
    ├── todos/
    │   ├── route.ts           ← GET, POST /api/todos
    │   └── [id]/
    │       ├── route.ts       ← PATCH, DELETE /api/todos/<id>
    │       └── toggle-done/route.ts  ← POST /api/todos/<id>/toggle-done
    ├── goals/...
    ├── habits/...
    └── ... (10개 도메인 별로)
```

**규칙:**
- `page.tsx` → 화면. URL 접속 시 보임
- `route.ts` → API 엔드포인트. fetch 받음
- `layout.tsx` → 공통 틀 (자식 페이지들을 감쌈)
- `[xxx]` → URL의 동적 부분 (`/annual/2026` 의 2026)
- `(xxx)` → 그룹 (URL 영향 없음, 폴더 정리용)

    ├── habitSchedule.ts

**왜 `lib/repo` 와 `lib/server/repos` 가 둘 다 있나?**
- `lib/repo/*.ts` (클라이언트): 브라우저에서 호출. fetch 만 함. SQL 모름.
- `lib/server/repos/*.ts` (서버): API route 가 호출. 실제 DB SQL 실행. 'server-only' 라 브라우저에서 import 불가.

같은 이름 (예: `todos.ts`) 의 두 파일이 있는 게 의도적입니다. 위/아래 역할이 다릅니다.

### 4.4 `store/` — 전역 상태 (Zustand)

```
store/
└── index.ts        · 전역 객체 (categories, goals, settings, me) + init/reload 메서드
```

페이지 여러 곳에서 같은 데이터(예: 카테고리 목록)를 쓸 때, 매번 fetch 하면 비효율. 한 곳(store)에 캐싱해두고 컴포넌트들이 가져다 씀.

```ts
// 컴포넌트에서 사용 예
const categories = useBinder(s => s.categories);
const me = useBinder(s => s.me);
```

### 4.5 `drizzle/` — DB 마이그레이션

```
drizzle/
├── 0000_petite_joshua_kane.sql      ← 첫 테이블 생성
├── 0001_demonic_screwball.sql       ← 스키마 변경 1
├── 0002_multi_user_schema.sql       ← users 테이블 추가
├── 0003_add_user_id.sql             ← 모든 도메인에 user_id 추가
├── 0004_settings_per_user.sql       ← settings 테이블 재구조
└── meta/
    ├── _journal.json                · 마이그레이션 순서 기록
    └── 0000_snapshot.json ...       · 각 시점의 스키마 스냅샷
```

스키마(테이블 모양)를 바꿀 때마다 `drizzle-kit generate` 가 SQL 파일을 자동 생성.
앱 시작 시 `lib/server/db/client.ts:getDb()` 가 자동으로 적용.

## 6. 인증 (로그인) 흐름

가장 헷갈리기 쉬운 부분. 단계별로:

```
1. 사용자가 /login 접속
   ↓ proxy.ts: /login 은 PUBLIC_PATHS 라 통과
2. 화면에 로그인 폼 (app/login/page.tsx)
3. 사용자가 username + password 입력 + 제출
   ↓
4. fetch('/api/auth/login', POST, { username, password })
   ↓ proxy.ts: /api/auth/login 도 PUBLIC_PATHS 라 통과
5. app/api/auth/login/route.ts:
   - verifyCredentials(username, password) 호출
   - lib/server/auth.ts: DB users 테이블에서 username 조회 → argon2.verify 로 비밀번호 검증
   - 성공: { userId, username } 반환
6. session.loggedIn = true, session.userId = ..., session.username = ...
   await session.save()
   ↓ Set-Cookie: binder_session=<암호화된 세션 데이터>
7. 클라이언트로 응답 { ok: true }
   ↓
8. 화면이 /(app)/main 으로 이동 (router.push)
9. 이후 모든 요청은 이 쿠키를 자동으로 함께 보냄
   ↓ proxy.ts: 쿠키 검증 → loggedIn === true 면 통과
10. API route 들이 requireSession() 으로 userId 꺼내 사용
```

**핵심 포인트**:
- 비밀번호는 평문으로 저장 안 됨 (argon2 해시만)
- 세션 정보(`userId` 등)는 쿠키 안에 **암호화** 되어 있음 (iron-session 이 `SESSION_SECRET` 으로 암호화)
- 쿠키는 30일 유효
- HTTPS 라야 쿠키가 전송됨 (`secure: true`)

## 7. DB 와 마이그레이션

**SQLite** 는 파일 한 개짜리 DB. 따로 서버를 안 띄움.

### 테이블 종류 (lib/server/db/schema.ts)

| 테이블 | 무엇을 담음 |
|---|---|
| `users` | 사용자 (id, username, password_hash) |
| `goals` | 만다라트 목표 (oneThing, mandalartCore, mandalartSub) |
| `annual_goals` | 연간 정량 목표 (월별 target/actual) |
| `categories` | 카테고리 (이름 + 색) |
| `todos` | 할일 (day/week/month/year 스코프) |
| `time_blocks` | 시간블록 (계획/실제) |
| `habits` | 습관 정의 |
| `habit_logs` | 습관 체크 기록 (날짜별) |
| `focus_notes` | "이 주의 한 문장" 같은 짧은 메모 |
| `retrospectives` | 일/주 회고 |
| `books` | 독서 기록 |
| `settings` | 사용자별 환경설정 |

**모든 도메인 테이블**(settings 포함)이 `user_id` 컬럼을 가지고, 모든 query 가 `user_id` 로 격리됩니다 → 사용자끼리 데이터 안 섞임.

### 마이그레이션 작동 방식

스키마 변경 시:
1. `lib/server/db/schema.ts` 의 테이블 정의 수정
2. `npx drizzle-kit generate` 실행
3. → `drizzle/0005_xxx.sql` 자동 생성됨
4. 다음 앱 시작 시 `getDb()` 가 자동 적용 (이미 적용된 마이그레이션은 skip)

운영 DB 에 적용은 `docker compose up -d --build` 만 하면 자동.

## 8. 배포 (Docker + Caddy)

운영 PC 에서 도는 컨테이너 두 개:

```
┌─ 인터넷 ────────────────────────────────────┐
│                                              │
│   사용자 (휴대폰/PC)                         │
│        │                                     │
│        │ HTTPS                               │
│        ↓                                     │
│   ┌────────────────────────┐                │
│   │ 공유기 (iptime)         │  포트포워드 80,443 │
│   │ young538.iptime.org    │                │
│   └────────────────────────┘                │
└────────│─────────────────────────────────────┘
         ↓ HTTPS (port 80, 443)
┌─ 운영 PC ────────────────────────────────────┐
│                                              │
│   ┌────────────────────────┐                │
│   │ Caddy 컨테이너          │                │
│   │ - HTTPS 종료 (self-signed)              │
│   │ - HTTP→HTTPS 리다이렉트                 │
│   └─────────┬──────────────┘                │
│             ↓ HTTP (port 3000, 내부망)       │
│   ┌────────────────────────┐                │
│   │ super-planner 컨테이너  │                │
│   │ - Next.js 앱            │                │
│   │ - DB: /app/data/...     │                │
│   └─────────┬──────────────┘                │
│             ↓ bind mount                     │
│   ./data/binder.sqlite (호스트 PC 파일)      │
└──────────────────────────────────────────────┘
```

- **Caddy** = 인터넷에서 들어온 HTTPS 요청을 받아 내부 앱으로 전달 (= 리버스 프록시)
- **앱 컨테이너** = 실제 Next.js 코드 실행
- **`./data/`** = 컨테이너가 꺼져도 데이터 보존 (호스트 파일을 컨테이너에 빌려줌 = bind mount)

## 11. 자주 헷갈리는 점

### Q1. `lib/repo/todos.ts` 와 `lib/server/repos/todos.ts` 차이?
- `lib/repo/` = **클라이언트(브라우저) 측**. fetch 만 함. SQL 모름.
- `lib/server/repos/` = **서버 측**. 실제 DB SQL 실행.
- 같은 도메인이라 같은 파일명이지만 사는 곳 (실행 환경) 이 다름.

### Q2. `'use client'` 첫 줄에 있는 파일과 없는 파일 차이?
- `'use client'` → 브라우저에서 실행되는 React 컴포넌트 (state, 이벤트 핸들러 가능)
- 없는 파일 → 서버에서 실행 (Server Component, 더 빠르고 SEO 유리하지만 state 못 씀)
- 이 프로젝트는 거의 모든 컴포넌트가 `'use client'` (간편함 우선)

### Q3. App Router vs Pages Router?
- 이 프로젝트는 **App Router** (Next.js 13+ 새 방식)
- `app/` 폴더 사용. `pages/` 폴더 안 씀.
- `app/posts/[id]/page.tsx` 가 `/posts/<id>` URL 에 해당.

### Q4. `[id]` 폴더 이름 대괄호?
- URL 의 동적 부분.
- `app/api/todos/[id]/route.ts` → `/api/todos/01ABC...` 등 모든 ID 매칭.
- 핸들러 안에서 `params.id` 로 추출.

### Q5. `(app)` 괄호 폴더?
- URL 에 안 들어감. 그룹핑 용도만.
- 로그인 후 페이지들에 공통 layout(네비) 적용하려고 묶음.

### Q6. middleware vs proxy?
- Next.js 13까지는 `middleware.ts`
- Next.js 16부터 `proxy.ts` 로 이름만 바뀜 (기능 동일)
- 모든 요청을 가로채는 게이트키퍼
